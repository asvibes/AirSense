# AirSense architecture

## Current local application

The current application is a Flask modular monolith. Flask serves the HTML page from `app/templates/alerts.html` and static CSS/vanilla JavaScript from `app/static/`; the JavaScript calls same-origin Flask APIs. The UI is integrated with the backend in code, but the repository has no automated browser end-to-end test or recorded browser verification.

The backend uses SQLAlchemy models with Alembic migrations. SQLite is the default local database; the SQLAlchemy URL and Alembic environment include PostgreSQL URL handling. As of 2026-11-05, the local SQLite database is at Alembic head `20261105_0004`, with the nullable `air_readings.received_at` column present. A fresh SQLite migration was compared with ORM metadata without reported differences; SQLite's expression-index reflection limitation required separate inspection of the room-name index. PostgreSQL schema/application compatibility has not been verified by an integration test, and no local PostgreSQL listener was available during the database audit. The separate SQL Server scripts under `database/migrations/` define a different proposed Azure SQL schema and are not used by the Flask app's Alembic migrations.

### Implemented local flows

- Session-based user registration, login and logout, with password hashes generated by Werkzeug's scrypt implementation.
- Home-scoped `owner` and `member` membership checks for protected API actions, plus CSRF validation for authenticated mutations.
- Owner-managed room creation and editing (name and ventilation sources), sensor provisioning, device-key rotation/revocation, threshold configuration, and invitations. Room deletion and role-change endpoints are not implemented.
- Sensor ingestion authenticated with an individual device key; only a peppered hash is stored. Simulator and DALTON replay use the shared reading/alert processing path and label their provenance.
- Threshold evaluation, alert lifecycle, history filters, CSV response, activity log, freshness calculation, and dashboard refresh.

### Current database records

The active ORM tables are `homes`, `users`, `home_memberships`, `home_invitations`, `rooms`, `sensors`, `metrics`, `threshold_policies`, `air_readings`, `air_alerts`, and `audit_logs`. The actual schema and its constraints are maintained in `app/models/` and `migrations/versions/`; see [data model](data-model.md). Readings store both event time (`measured_at`) and nullable server receipt time (`received_at`); existing readings without known receipt times remain null. Notable PRD differences: roles are `owner`/`member` rather than global standard-user/manager/admin roles.

## Local trust boundaries and controls

- **Browser to Flask:** Same-origin session cookies, HttpOnly and SameSite settings, CSRF checks on authenticated mutations, server-side membership/role checks, and input validation are implemented. HTTPS is not provided by the local development server.
- **Sensor to ingestion API:** The `X-Device-Key` is checked against a stored peppered hash; sensors can be revoked and keys rotated. The configured limiter is process-local, and unknown or revoked devices are rejected.
- **Flask to database:** SQLAlchemy/ORM expressions are used by the active application. SQLite foreign-key enforcement is enabled for application SQLite connections. Back up data before any migration.
- **Relational scope:** Foreign keys ensure referenced homes, rooms, sensors, and metrics exist, but separate `home_id` and `room_id` FKs do not guarantee they refer to the same home. Application paths enforce scope; the active schema lacks the composite same-home FKs used in the separate SQL Server target.
- **Audit:** Selected account, membership/invitation, room, sensor, threshold, reading, and alert events are recorded. There is no role-change feature; failed logins for unknown accounts cannot be written to a home-scoped log.

These are local code controls, not evidence that a production deployment has been secured. Security headers, deployed HTTPS, least-privilege hosted database identities, database firewall/network restrictions, private Blob access, retention, backup/recovery, and incident response remain future/unverified deployment work.

## Proposed target architecture (not deployed)

The PRD proposes hosting the application and relational data in Azure, using Blob Storage for supporting files/reports, and a separate Power BI report for descriptive analytics. These are target/submission requirements, not active integrations. The tracked `database/powerbi/airsense-report.pbix` is empty, the app has no Blob Storage integration, and the Azure SQL scripts are not wired into the application.

The proposed reading flow is: a physical device or clearly labelled simulator sends a timestamped measurement; the API authenticates and validates it; the application records it and evaluates thresholds transactionally; authorized users view current state/history; and a controlled historical dataset can be consumed by Power BI. No Azure service connection, cloud deployment, or cloud integration test is claimed.

## Target data and analytics controls

If cloud deployment proceeds, use HTTPS, private secret configuration, least-privilege database credentials, network restrictions, private Blob containers and scoped access, and read-only analytics access where practical. Validate these controls in the actual deployment before using real personal or household data. Power BI/Blob data flow, licensing, retention, and access policy still require design and verification.
